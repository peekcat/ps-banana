### 1.2 加规则的方式（与任务单写法不同，重要）

任务单建议用 Merge 的 `prepend-rules`。**在这台机器的 2.5.8 上无效**，实测过程：

1. 在全局 Merge（`profiles/Merge.yaml`）写入 `prepend-rules` 三条；
2. 生成的运行时配置 `clash-verge.yaml` 里出现的是**字面量**顶层键 `prepend-rules:`，`rules:` 列表（第 600 行起）中**没有**这三条；
3. 内核把 `prepend-rules` 当未知字段忽略，规则**实际没生效**。

改用**全局扩展脚本** `profiles/Script.js`（Clash Verge 的「全局扩展脚本」，对全部订阅生效，订阅刷新不影响）：

```js
function main(config, profileName) {
  var blocked = [
    "DOMAIN,xiasanqi.cpolar.top,REJECT",
    "DOMAIN,xiasanqiforge.vip.cpolar.cn,REJECT",
    "DOMAIN,qwentest.vip.cpolar.top,REJECT"
  ];
  if (typeof config !== "object" || config === null) return config;
  var rules = Array.isArray(config.rules) ? config.rules : [];
  var kept = rules.filter(function (r) { return blocked.indexOf(r) < 0; });
  config.rules = blocked.concat(kept);
  return config;
}
```

用 `DOMAIN` 精确匹配就够：三个域名在插件里都是裸主机名，没有子域名（`core/server-config.js:10`、`:17`，`tiles/tile-qwen21.js:20`）。

**运行时确认**：`GET http://127.0.0.1:9097/rules` 返回的 44 条规则里，**前三条**就是这三个域名的 `REJECT`。

> 修改前的原件都已备份：`profiles/Merge.yaml.bak-psbanana-20261026-213134`、`profiles/Script.js.bak-psbanana-20261026-214900`、`verge.yaml.bak-psbanana`。

### 1.3 curl 验证（刷新订阅前）

```powershell
curl.exe -sS -m 10 -x http://127.0.0.1:7897 -o NUL -w "%{http_code}`n" https://xiasanqi.cpolar.top/
curl.exe -sS -m 10 --noproxy "*" -o NUL -w "%{http_code}`n" https://xiasanqi.cpolar.top/
```

| 域名 | 走代理（7897） | 不走代理 |
|---|---|---|
| `xiasanqi.cpolar.top` | `curl: (35) schannel: failed to receive handshake` · code=000 · **3 ms** | `curl: (6) Could not resolve host` · **14 ms** |
| `xiasanqiforge.vip.cpolar.cn` | 同上 · code=000 · **3 ms** | 同上 · **20 ms** |
| `qwentest.vip.cpolar.top` | 同上 · code=000 · **3 ms** | 同上 · **5 ms** |

**对照组**（证明不是「网不通」或「服务器本来就挂」）：

| 对照 | 结果 |
|---|---|
| `https://nonexistent-psbanana-9f3a.cpolar.top/` 走代理 | **HTTP 404**，285 ms（cpolar 泛域名应答，链路正常） |
| 同上，不走代理 | **HTTP 404**，294 ms |
| `https://www.baidu.com/` 走代理 | **HTTP 200** |

走代理时 3 ms 就被掐断（远低于任何网络 RTT），且内核日志明确记录命中的是 `Domain(xiasanqi.cpolar.top) using REJECT` —— **屏蔽确实由规则生效，不是 DNS 或服务器状态**。

不走代理时 `curl: (6)` 是因为 hosts 里三个域名仍是 `0.0.0.0`（`Resolve-DnsName` 确认），连接目标非法，连接没建立就失败。

### 1.4 刷新订阅之后

**这项没做成**：Clash Verge 的自动订阅更新在日志里是 `403 Forbidden`（订阅地址或 token 失效），手动刷新同样拿不到新内容：

```
[Config] [订阅更新] 直接更新失败: ... os error 10054，尝试使用Clash代理更新
[Config] [订阅更新] Clash代理更新失败: ... status 403 Forbidden，尝试使用系统代理更新
[Config] [订阅更新] 系统代理更新失败: ... status 403 Forbidden，所有重试均已失败
```

不过这一项对结论没有影响：规则写在 `Script.js` 而不是订阅文件里，**即使订阅刷新成功也不会丢**。我在两次重启 Clash Verge（每次都会重新生成 `clash-verge.yaml` 并重载内核）后都确认了 `/rules` 前三条仍在，等价于「配置重建后规则仍在」。

### 1.5 UXP 插件的请求走不走系统代理 → **走**

这是任务单第 4 小项要的答案，而且比「在 GUI 里肉眼看连接页」更硬：直接订阅内核日志（`ws://127.0.0.1:9097/logs?level=info`）抓到的原始行：

```
[21:57:40.383] {"type":"info","payload":"[TCP] 127.0.0.1:5398 --> xiasanqi.cpolar.top:443 match Domain(xiasanqi.cpolar.top) using REJECT"}
[21:57:40.391] {"type":"info","payload":"[TCP] 127.0.0.1:5399 --> xiasanqi.cpolar.top:443 match Domain(xiasanqi.cpolar.top) using REJECT"}
```

- 整个会话期间 `xiasanqi.cpolar.top` 共被 **REJECT 40 次**（21:57:40 – 22:27:25），每一次都对应插件里一次真实请求；
- 每个 HTTP 请求产生 **2 条 TCP 连接**（相隔几毫秒），是 IPv6/IPv4 双栈各试一次；
- 三次 curl 之外的所有 REJECT 都能在插件侧日志里找到对应动作（公告、登录、验证码、Momo 链接、图床上传），**没有一条是 curl 造成的**。

**推论**：UXP 的 `fetch` 走系统代理，所以「只改 hosts」在有代理的机器上确实不够，任务单的判断是对的。

### 1.6 额外实测：三个域名在公网仍然解析（与「停服」的关系）

用阿里公共 DNS 的 DoH（`https://223.5.5.5/resolve`，走 IP 直连，不受本机 hosts 影响）：

| `xiasanqi.cpolar.top` | CNAME `cpolard-c.cpolar.top` → `116.211.150.208` |

### 2.3 为什么 4a / 4c 无法执行

`tiles/tile-run.host.js:465`：引擎是 `api`/`forge` 时**一定**抓选区；抓不到直接 `throw new Error("未检测到选区")`（`:533`）。设置里「无选区自动全图」开关默认关，描述就是「默认关：必须先建选区」（`tiles/tile-settings.js:278`）。

GPT-Image 那条更死：`tiles/tile-run.host.js:617-635` 把 `captureBase64` 一并塞进 `_allRefs` 上传图床，而 `_allRefs` 为空时直接抛 `GRS+GPT-Image 模式需要至少一张图作为参考`。

- **「Banana 文生图（不带图）」没有入口** —— 只要走单图生成就必须有选区，有选区就带参考图；
- **「GPT-Image 纯文生图（不带图）」也没有入口** —— 有图必上传图床（即第 5 项的失败），无图直接报错。

任务单 4a/4c 与第 5 项在 6.6.4 上无法分离，C 阶段改造时这一点需要重新设计测试方案（例如改造后新增「不附带参考图」的调用路径，或直接用 `tools/grs_probe.py` 单独验接口）。

## 3. 和预期不一致的地方

### 3.1 端口：文档写 7892，实际 7897

`docs/Windows测试端准备.md` 第 9 节写「系统代理 `127.0.0.1:7892`」。实测：7892 **无监听**，Clash Verge 的 `verge_mixed_port` 是 **7897**，系统代理也指向 7897。注册表里残留的 `ProxyServer=127.0.0.1:7892` 是旧值（`ProxyEnable=0` 期间不会被使用）。**按文档用 7892 做验证会得到「连接被拒」，看起来像屏蔽成功，其实是端口不对** —— 建议 Mac 端改文档。另外这轮把 TUN 关掉了（开着时所有进程流量都被吞掉，测不出「UXP 走不走系统代理」，而且 fake-ip 会干扰 hosts 证据）。

### 3.2 Merge 的 `prepend-rules` 在 2.5.8 上无效

见 §1.2。文档给的写法在这台机器上不生效，改用全局扩展脚本。Mac 端若要写进文档，建议直接写 Script 方案。

### 3.3 DevTools 的 Network 面板看不到作者域名的请求

任务单要求「Network 里打向被屏蔽域名的请求（URL + 发起位置）」。实测**一条都没有**，不是操作问题：

- 插件 UI 是 `index.html` 里的 `<webview src="plugin:/panel.html">`；
- 所有访问作者服务器的请求都在 **host 层**（`login-service.js:165`、`tiles/*.host.js`，运行在 Photoshop 宿主进程）；`core/server-config.js` 只被 `*.host.js` 和 `login-service.js` 引用，面板侧没有。
- UDT 的 DevTools 只记录面板 webview 自己的网络请求。

本轮改用**内核日志 + 插件宿主日志**（`UXPLogs_*.log`）取证，反而更准（能看到命中哪条规则、时间戳精确到秒）。后续轮次建议直接把「看 Network」换成「抓这两份日志」，方法见 §5。
