# GRS 参考图 base64 实测记录（去云化评估 §5.1 验证）

- 测试时间：2026-10-26 17:09–17:20（Asia/Shanghai）
- 线路：`https://grsai.dakka.com.cn`（GrsAI 国内节点）
- 模型：`gpt-image-2-vip`，1K（`aspectRatio: "1024x1024"`）
- 消耗：账户 50000 → 42000 积分，4 张图共 8000 积分（按 GrsAI 站内汇率 ¥1 = 20000 积分，约 ¥0.4）
- 脚本：`tools/grs_probe.py`；原始请求/响应与结果图在 `docs/实机记录/grs-probe/`（已 gitignore，不入库）
- 证据拼图：`docs/实机记录/assets/grs-b64-probe-2026-10-26.png`

## 结论

**旧接口 `POST /v1/draw/completions` 的 `urls` 字段直接收 `data:image/png;base64,...`，新接口 `POST /v1/api/generate` 的 `images` 字段也收。两个方案都成立，且多张参考图可用。**

这意味着 §5.1 里「GRS × GPT-Image × 带图必须先上传到作者临时图床」的前提不成立：**不需要任何图床，也不需要 `support.deviceId`**。改造量从「重写提交与轮询」降到「删掉上传步骤、把 base64 塞进 `urls`」。

| 测试 | 接口 | 参考图字段 | 结果 | 耗时 | 判定 |
|---|---|---|---|---|---|
| 1 | `POST /v1/api/generate` | `images: ["data:image/png;base64,…"]` | `status: succeeded`，返回 1 个 URL | 33.3 s（同步返回） | ✅ 红方块变蓝，位置/尺寸不变 |
| 2 | `POST /v1/draw/completions` | `urls: ["data:image/png;base64,…"]` | `code: 0` → 轮询 `succeeded` | 52.4 s（提交 0.1 s + 轮询） | ✅ 红方块变蓝 |
| 3 | 旧接口，2 张参考图 | `urls: [dataURI_红方块, dataURI_绿圆]` | `code: 0` → 轮询 `succeeded` | 40.0 s | ✅ 红方块与绿圆同时出现在输出里 |
| 4 | 新接口，`replyType: "async"` | `images: ["data:image/png;base64,…"]` | 提交即返回 `{id, status:"running"}` → `GET /v1/api/result` 轮询 `succeeded` | 40.1 s（提交 0.1 s + 轮询） | ✅ 红方块变蓝，异步链路可用 |

判定方式不是「看起来像」，而是对结果图做像素占比统计：原图红块约占 30%；测试 1/2/4 结果红色 0.0%、蓝色 26.5–33.0%；测试 3 红色 16.7% + 绿色 13.0%。颜色被精确改掉/保留，说明模型确实读到了参考图，不存在「忽略参考图、凭空画一张」的情况。

官方 Apifox 文档也明确写了 `images` **「支持 base64 与 url 链接」**（见下节），所以方案 2 不是社区猜测，有文档依据；方案 1 则是旧接口上的未文档化行为，属于实测通过。

对本次测试的说明：

- 测试 1 用的 body 里带了从旧接口抄来的 `webHook` / `shutProgress`，并**没有**传 `replyType`；服务端按 JSON 同步处理并返回结果。官方写法应该是 `replyType: "json"`，这两个旧字段不属于新接口文档。
- 测试 1 的 `aspectRatio: "1024x1024"` 符合 VIP 的「只收像素值」约束。
- 旧接口 `/v1/draw/completions` 仍在 grsai.com 的旧文档页里，插件当前用的就是它；Apifox 新文档只列 `/v1/api/generate`。

## 测试方法

输入图（本地生成，640×480 白底）：

- 红方块：`(160,120)-(480,360)`，纯 `#FF0000`
- 绿圆（仅测试 3）：同区域绿色 `#00AA00` 圆

Prompt：

- 单图：`Edit the reference image: change the red square to blue (#0000FF). Keep the white background and the square's exact position and size unchanged. Flat vector illustration, no text.`
- 双图：`Combine the two reference images onto one white background: keep the red square from the first image on the left and the green circle from the second image on the right. Same colors and sizes, flat vector illustration, no text.`

## 测试 1：新接口 + base64

请求：

```http
POST https://grsai.dakka.com.cn/v1/api/generate
Authorization: Bearer <key>
Content-Type: application/json

{
  "model": "gpt-image-2-vip",
  "prompt": "…",
  "images": ["data:image/png;base64,iVBORw0KG…"],
  "aspectRatio": "1024x1024",
  "webHook": "-1",
  "shutProgress": true
}
```

响应（HTTP 200，33.3 s，`application/json`）：

```json
{"id":"7-1b112c6a-b133-4b6a-8121-50b182ed56af","status":"succeeded","results":[{"url":"https://file5.aitohumanize.com/file/a230dd…png"}],"progress":100}
```

观察：

- 新接口是**同步**的：一次 POST 直接拿到 `status: succeeded` 和结果 URL，不需要轮询。
- 随后用 `GET /v1/api/result?id=<id>` 取结果返回 404 `{"error":"result not exist, valid for 2 hours"}`。同步模式（`replyType:"json"`）不落可查询的结果记录，所以这个 id 查不到；异步模式（`replyType:"async"`）可以正常查询，见测试 4。改造时同步模式直接用响应里的 URL 即可。
- 结果 1024×1024：红色 0.0%、蓝色 28.7%、白色 70.1%。

## 测试 2：旧接口 + base64 放进 urls

请求：

```http
POST https://grsai.dakka.com.cn/v1/draw/completions
Authorization: Bearer <key>
Content-Type: application/json

{
  "model": "gpt-image-2-vip",
  "prompt": "…",
  "aspectRatio": "1024x1024",
  "webHook": "-1",
  "shutProgress": true,
  "urls": ["data:image/png;base64,iVBORw0KG…"]
}
```

提交响应（0.1 s）：

```json
{"code":0,"data":{"id":"13-bc343326-afc3-43fe-8db7-ec2ff35bc691"},"msg":"success"}
```

轮询 `POST /v1/draw/result` `{"id": "13-…"}`：`running progress 5` → `60` → `succeeded`（总耗时 52.4 s），`results[0].url` 即结果图。

结果 1024×1024：红色 0.0%、蓝色 26.5%、白色 72.4%。**这就是插件现有链路（`callGrsGptImageApi`）去掉图床后的样子，改动最小。**

## 测试 3：旧接口 + 多张 base64

`urls` 传两个 data URI（红方块、绿圆），一次提交成功，40.0 s 完成。结果红色 16.7%、绿色 13.0%、白色 69.2%，两个图形都在、颜色未串。

说明插件里「主图 + N 张参考图」打包成一个数组的用法可以直接保留，只需把数组元素从公网 URL 换成 data URI。

## 测试 4：官方异步模式（`replyType: "async"`）

官方 `replyType` 有 `json` / `stream` / `async` 三种。异步模式对插件更稳：POST 立刻拿 id，再轮询结果，不受单次 fetch 超时影响。

请求体（不再需要旧接口的 `webHook` / `shutProgress`）：

```json
{
  "model": "gpt-image-2-vip",
  "prompt": "…",
  "images": ["data:image/png;base64,iVBORw0KG…"],
  "aspectRatio": "1024x1024",
  "replyType": "async"
}
```

提交响应（0.1 s）：

```json
{"id":"14-52dc7baa-a770-4c9e-929e-3d6a09582ec2","status":"running"}
```

轮询 `GET /v1/api/result?id=14-52dc7baa-…`：`running progress 10` → `succeeded progress 100`，总耗时 40.1 s，`results[0].url` 即结果图。

结果 1024×1024：红色 0.0%、蓝色 33.0%。**官方异步链路完整可用**，包括 `GET /v1/api/result`。

## 对改造方案的影响

按 §5.1 原方案表更新：

| 方案 | 现状 | 建议 |
|---|---|---|
| **1. 旧接口塞 base64** | **已实测可用**（单图、多图均通过）；官方旧文档仍列该端点，但 `urls` 收 data URI 属未文档化行为 | **推荐（改动最小）**：删掉 `_uploadRefsToTempServer`，`payload.urls` 直接放 data URI；提交/轮询逻辑一行不用改 |
| 2. 换新接口 `/v1/api/generate` | **已实测可用**，官方文档明确 `images` 支持 base64/url；`json` 同步与 `async` 轮询两条路都验证过 | 备选/后续：按官方文档重写提交与轮询，能拿到 `quality` / `background` / `mask` 等新参数，也避免依赖旧接口 |
| 3. 用户自配图床 | — | 不再需要 |
| 4. 放弃组合 | — | 不再需要 |

方案 1 的落地位置（两处）：

- `plugin/tiles/tile-run.host.js:617-661`：去掉 `_uploadRefsToTempServer` 整段，改为把 `_allRefs` 的 base64 直接带进 `callAiApi`（或直接构造 `grsUrls`）。
- `plugin/tiles/tile-poster.host.js`：同样的上传调用一并删。

方案 2 如果要落地：`callGrsGptImageApi` 改为 `POST /v1/api/generate` + `replyType: "async"`，轮询换成 `GET /v1/api/result?id=`，响应结构从 `{code,data:{status,results}}` 改为 `{status,results}`（`violation` 也要当失败处理）。

附带收益：用户图片不再经过作者服务器；不再依赖 `support.deviceId`；`_ensureSmallEnough` 的 1.2 MB 强制压缩（原本是为 cpolar 的 2 MB 上限）可以放宽甚至去掉。

## 成本与额度

- 每张 1K `gpt-image-2-vip` 扣 **2000 积分**（4 张共 8000）。
- 余额查询：`POST /client/openapi/getAPIKeyCredits`，body `{"apiKey": "…"}`，返回 `{"code":0,"data":{"credits":42000,…}}`。
- 结果图 URL 由 `file3/file4/file5/file6.aitohumanize.com` 提供，官方文档说明有效期 2 小时，需及时转存。

## 尚未验证 / 风险

1. **请求体上限**：本次只用了 2.6 KB 的 base64。插件现在压到 1.2 MB，若放宽需要实测 GRS 的 body 上限（第三方项目称 24 MB，未证实）。建议第一版保留 1.2 MB 压缩，先修通链路，再单独做体积测试。
2. **JPEG / 透明通道**：只测了 PNG data URI。插件传 PS 截图通常是 PNG，参考图可能是 JPEG，格式理论上不影响 base64 解码，但未实测。
3. **4K 与长任务**：新接口 `replyType:"json"` 同步返回在 1K 下 33 s；4K 或排队时可能超过插件单次 fetch 超时。用 `replyType:"async"` + `GET /v1/api/result` 可以规避（本次已用 1K 验证异步链路，4K 未测）。旧接口本身也是轮询，没有这个问题。
4. **旧接口 `urls` 收 base64 属于未文档化行为**：官方 Apifox 新文档只写 `/v1/api/generate` 的 `images` 支持 base64/url，旧端点虽仍在 grsai.com 旧文档里，但 `urls` 收 data URI 没有文档承诺，未来可能收紧。建议保留「失败则回退新接口」的分支。
5. 本次测试图是合成图，真实 PS 选区/人像的压缩伪影、审核策略未覆盖。

## 附：`grsai.dakka.com.cn` 是谁的域名？

**结论：GrsAI 的国内 API 节点，不是插件作者部署的。** 依据：

1. **官方文档就写的这个地址。** `https://grsai.com/zh/dashboard/documents/gpt-image` 页面里 API 基址输入框的值是 `https://grsai.dakka.com.cn`，接口示例是 `https://grsai.dakka.com.cn/v1/draw/completions`；用户提供的接口文档也写明 `POST https://{base_url}/v1/api/generate`，全球节点 `https://grsaiapi.com`、国内节点 `https://grsai.dakka.com.cn`。
2. **域名注册人是 GrsAI 的开票主体。** WHOIS：`dakka.com.cn` 注册人「打卡（广州）科技有限公司」，注册时间 2022-12-29，注册商腾讯云，NS 为 DNSPod。GrsAI 站内的开票公司列表里就有「打卡（广州）科技有限公司」。
3. **基础设施是商业多节点，不是内网穿透。** `grsai.dakka.com.cn` 解析到 3 个腾讯云 IP（114.66.27.113 / 114.66.59.231 / 110.42.111.33），nginx 1.23.4，TrustAsia DV 证书（2026-10-06 至 2027-01-04）。
4. **作者自己的后端是另一套。** README 记录作者后台为 `https://xiasanqi.cpolar.top`（cpolar 内网穿透），与 `dakka.com.cn` 无关。

需要注意的边界：

- GrsAI 本身也不是模型原厂，其官网自称「大模型 API 源头**中转**站 / 聚合平台」，属于第三方转售。BYOK 只是「不经过插件作者」，仍然依赖 GrsAI 这家第三方继续经营。
- 无法从公开信息证明或排除「作者与打卡科技存在合作/关联」。能确定的是：这个域名由打卡科技注册、被 GrsAI 官方文档公布为国内节点，不属于作者那套 cpolar 后端。
- 插件的「夏算力托管」模式走的是作者服务器签发的子 Key，那是另一条链路；BYOK 模式才是直连本节点。
